# 售后答案格式

当前 Agent 内部使用 Pydantic `SupportAnswer` 结构化输出。SDK output guardrail 会在渲染前检查结构化输出；runtime 还会对内部中文文本做本地 contract 校验。

终端回答保留以下结构和字段顺序，作为调试和验收格式：

```text
AI 客服参考

问题类型：
product_usage / troubleshooting / quality_issue / ticket_followup / unknown

运行模式：
Agent SDK

置信度：
高 / 中 / 低，并说明原因。

用户问题摘要：
...

SKU 命中：
- 如果命中：SKU / SPU / 品名 / 产品负责人 / 命中置信度
- 如果未命中：未在 SKU 目录中命中；需要补充订单 SKU、包装 SKU、产品铭牌或图片。

建议回复（供客服参考，可复制调整）：
...

建议排查步骤：
1. ...
2. ...
3. ...

需要追问：
- ...

正式依据：
- 文档名称 / 章节 / 链接
- 如果未查询到：未查询到可信正式依据，不可编造。

历史参考：
- 相似案例摘要 / 日期 / 链接
- 如果未查询到：未查询到可信历史参考，不可编造。

工单草稿：
- 如果需要：标题 / 问题描述 / 缺失信息 / 建议负责人 / 优先级 / 下一步
- 如果不需要：不建议生成工单，并说明原因。
```

## 依据规则

- SKU 字段只能来自 `search_sku_catalog` 或用户消息本身。
- 正式依据只能来自已接入的正式知识库/RAG 结果。
- 历史参考可以来自已接入的已审核群聊历史 FAQ 或后续结构化案例卡片结果。
- 如果检索工具说明未接入或没有命中，答案必须说明没有找到可信依据。
- 不得编造文档名、章节、链接、历史案例、批次结论、负责人、政策或技术结论。

## 置信度规则

- 高：已接入的正式依据直接匹配产品和问题，或回答仅限于直接 SKU/产品识别。
- 中：SKU/产品身份清楚且命中已审核群聊历史 FAQ，但缺少正式政策源，或排查建议仍需要确认。
- 低：没有正式依据、没有已审核历史案例、仅命中媒体观察、SKU 不明确，或用户消息过短。

SKU 命中置信度和整体答案置信度是两件事。精准 SKU 命中可以让 `SKU 命中` 高置信，但如果正式知识库和已审核历史检索都没有命中，整体答案置信度必须为低。

低置信度时，答案必须提醒客服在回复客户前人工确认。

仅命中媒体观察证据时，`recommended_action` 上限为 `human_review`。媒体观察可以帮助描述图片/视频里看到的事实，但不能单独支撑正式技术结论、政策依据、判责、退款、换新、补发或处理时效。

## 飞书可见回复

飞书群里不直接发送上述 11 字段格式。runtime 会把 `SupportAnswer` 再渲染成面向客服同事的自然中文：

- 使用 2-4 个自然段，不使用 Markdown 标题、项目符号、表格、代码块或粗体。
- 不出现 `SupportAnswer`、`Agent SDK`、证据包、guardrail、contract、trace、tool 等内部术语。
- 不出现 `问题类型：`、`运行模式：`、`正式依据：`、`历史参考：`、`工单草稿：` 等字段标签。
- 不出现“未查询到可信正式依据”“未审核媒体观察证据”等内部检索话术；需要用“目前材料还不够直接下结论”“需要人工复核后再给客户明确口径”等自然表达。
- 仍必须保留售后安全边界：不得直接承诺退款、赔付、换新、补发或处理时间。

如果飞书可见回复校验发现内部字段、Markdown 痕迹或售后承诺风险，runtime 发送安全 fallback：`这轮没有生成到足够稳妥的建议，请人工接手确认后再回复客户。`
